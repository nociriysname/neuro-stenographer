# Архитектура решения

> Черновик технического анализа на старте хакатона (07.11.2026). Цифры скорости и качества, помеченные
> «оценка», ещё не измерены на устройстве. Реальные замеры будут в [TEST_RESULTS.md](TEST_RESULTS.md).

## Контекст

**Задача.** Android-приложение, которое полностью на устройстве превращает запись разговора в
структурированную расшифровку: кто говорил, когда и что. Результат показывается в приложении и
экспортируется в JSON по формату из ТЗ ([PROTOCOL.md](PROTOCOL.md)).

**Как проверяют.** Эксперты ставят наш APK, импортируют три записи «диалогов котиков», запускают
обработку, экспортируют результат и сравнивают его с эталоном. Интернета нет, облако запрещено,
локальная LLM обязательна.

**Критерии и что из них следует:**

| Критерий | Баллы | Что это значит для архитектуры |
|---|---:|---|
| Точность транскрибации (WER) | 40 | Главное. Лучшая доступная модель русского ASR, аккуратная нарезка, без порчи текста LLM |
| Точность диаризации | 25 | Сильная диаризация с перекрытиями; слова назначаем спикерам по таймкодам |
| Точность временных меток | 10 | Границы реплик берём из таймкодов слов, а не из сегментов диаризации |
| Скорость (RTF) | 10 | int8/q8 веса, CPU-потоки, пропуск тишины, последовательная загрузка моделей |
| Работоспособность и UX | 10 | Прогресс по этапам, плеер с переходом к реплике, понятные ошибки |
| Защита | 5 | Понимаем каждое решение; экран «О моделях», метрики собственного стенда |

Вывод: **75 баллов из 100 зависят от качества моделей и склейки их результатов.** UI делаем аккуратным,
но не за счёт времени на ASR и диаризацию.

## Конвейер обработки

```
Файл / запись с микрофона
  │  MediaExtractor + MediaCodec → моно float, windowed-sinc ресемплинг → 16 кГц   (common-audio)
  ▼
Диаризация — Nemotron-3-Diarization                                             (core-diarization)
  │  вероятности активности 8 спикеров с шагом 10 мс → сегменты [спикер, начало, конец]
  ▼
Нарезка — ChunkPlanner                                                           (core-domain)
  │  объединение сегментов = участки речи (диаризация работает как VAD);
  │  фрагменты ≤ 20 с с границами в паузах, тишина пропускается
  ▼
ASR — GigaAM-v3                                                                  (core-asr)
  │  слова с абсолютными таймкодами
  ▼
Сборка — TranscriptAssembler                                                     (core-domain)
  │  слово → спикер с максимальным перекрытием; склейка в реплики; speaker_1…N по первому появлению
  ▼
Постобработка                                                                    (core-llm)
  │  текст не меняется: организаторы просили дословную расшифровку
  ▼  по кнопке «Протокол»
Протокол встречи — LFM3-1.7B + LoRA, llama.cpp                                    (core-llm)
  │  краткое содержание, решения, задачи с исполнителем и сроком; длинные записи — по частям
  ▼
JSON по ТЗ + TXT + SRT, экран результата                                         (core-data, feature-transcript)
```

**Почему диаризация идёт до ASR.** Её сегменты нужны дважды: чтобы резать запись в паузах (нельзя
разрезать слово, иначе растёт WER) и чтобы назначать слова спикерам. Отдельный VAD не нужен.

**Почему реплика определяется словами, а не сегментами.** Сегменты диаризации захватывают паузы и
«дышат» на краях, а таймкоды слов от ASR точнее. Поэтому начало реплики — начало первого слова,
конец — конец последнего. Это напрямую влияет на 10 баллов за временные метки.

Конвейер уже реализован в `TranscribeAudioUseCase` и покрыт тестами на фейковых движках. Не хватает
только настоящих движков.

## Модели и их интеграция

### GigaAM-v3 — распознавание речи

[ai-sage/GigaAM-v3](https://huggingface.co/ai-sage/GigaAM-v3), MIT. Conformer на 220–240M параметров,
предобучен на 700 тыс. часов русской речи. Вход — 16 кГц, 64 mel, hop 10 мс, subsampling ×4,
то есть один кадр энкодера на 40 мс.

| Вариант | Средний WER, % (из карточки модели) | Комментарий |
|---|---:|---|
| `rnnt` | **8.4** | Лучший WER, текст без пунктуации |
| `ctc` | 9.2 | Быстрее декодируется, таймкоды точнее |
| `e2e_rnnt` / `e2e_ctc` | — | С пунктуацией и нормализацией текста (числа цифрами) |
| Whisper (для сравнения) | 25.1 | Почти втрое хуже на русском |

**Рантайм: sherpa-onnx 2.0.1** (ONNX Runtime, Kotlin API). У k2-fsa есть конвертации всех вариантов v3
(asr-models, 16.12.2025), энкодер int8:

- `sherpa-onnx-nemo-transducer-punct-giga-am-v3-russian-2025-12-16` — e2e_rnnt, словарь SentencePiece на 1024 токена;
- `sherpa-onnx-nemo-transducer-giga-am-v3-russian-2025-12-16` — rnnt, посимвольный словарь (33 буквы и пробел);
- `…-ctc-…` — CTC-варианты, пока не используем.

**Как сделано в `core-asr`:**

1. AAR sherpa-onnx публикуется только в GitHub Releases. Берём вариант `sherpa-onnx-static-link-onnxruntime`
   (38 МБ): ONNX Runtime слинкован внутрь `libsherpa-onnx-jni.so` и не конфликтует со своим
   `onnxruntime-android`, если он понадобится позже (например, для эмоций). `fetch_models.sh` кладёт AAR
   в локальный Maven-репозиторий `src/android/third_party/maven`, и Gradle берёт его как обычную
   зависимость из каталога версий. Прямой `files("x.aar")` в библиотечном модуле AGP не разрешает.
2. Веса — `encoder.int8.onnx` (225 МБ), `decoder.onnx`, `joiner.onnx`, `tokens.txt` из архива k2-fsa —
   лежат в `assets/models/gigaam-v3-<вариант>/`. В APK кладётся один вариант (`fetch_models.sh --asr=…`),
   `GigaAmSpeechRecognizer` берёт тот, что есть на устройстве. При первом запуске `ModelInstaller`
   копирует файлы в `noBackupFilesDir` (1.7 с на эмуляторе).
3. `OfflineRecognizer`: `model_type = nemo_transducer`, 64 mel, greedy search, 4 потока. Остальные параметры
   признаков sherpa-onnx берёт по флагу `is_giga_am` из метаданных модели.
4. Модель загружается 3–3.5 с и занимает ~230 МБ, поэтому в порт `SpeechRecognizer` добавлен
   `withModelLoaded { }`: конвейер загружает GigaAM один раз на все фрагменты и освобождает её до LLM-этапа.
5. Слова собираются из токенов (`tokensToWords`): для SentencePiece — по маркеру `▁`, пунктуация
   приклеивается к слову; для посимвольного словаря — по токену-пробелу. Начало слова — таймкод первого
   токена, конец — кадр (40 мс) после последнего, но не позже начала следующего слова. Границы реплик
   конвейер берёт по словам, поэтому запас `pad_onset` диаризации на них не влияет.

**Какой вариант оставить для сдачи — решаем по нормализации организаторов.** Если в эталоне «две тысячи
двадцать пять», то e2e («2025») даст ошибку на ровном месте; то же с дефисами («нейро-стенографист» против
«нейростенографист»). Сейчас по умолчанию e2e_rnnt: читаемый текст сразу с пунктуацией. На тестовом
диалоге оба варианта дали WER 2 %, rnnt в единичном замере декодировал быстрее (2.5 с против 4.4 с на
32 с аудио). Окончательно выбираем после ответа организаторов, вопросы в конце документа.

### Nemotron-3-Diarization — кто говорит

[nvidia/Nemotron-3-Diarization](https://huggingface.co/nvidia/Nemotron-3-Diarization), OpenMDW-1.1
(коммерческое использование разрешено), релиз 23.09.2026.

- Sortformer, 100M параметров, до **8 спикеров**, обрабатывает **перекрывающуюся речь**.
- Выход — тензор `[T, 8]` вероятностей активности с шагом 10 мс. Каналы упорядочены по первому
  появлению спикера, что удобно для нумерации `speaker_N`.
- Для длинных записей — Arrival-Order Speaker Cache. Офлайн-пресет: буфер 30.4 с,
  `spkcache=264, fifo=40, chunk=340, right_context=40, update_period=300`.
- DER по сравнению с прошлой моделью `diar_streaming_sortformer_4spk-v2.1`: CALLHOME 9.10 против
  10.32, DIHARD III 12.73 против 19.09.

**Рантайм: NeMo-Speech.cpp** ([NVIDIA/NeMo-Speech.cpp](https://github.com/NVIDIA/NeMo-Speech.cpp),
Apache-2.0). Это C++ рантайм на ggml со стабильным C ABI `include/nemo_speech/diar.h`:

```c
nemo_speech_diar_create(&cfg /* model_path, preset = "v3-offline" */, &model);
nemo_speech_diar_stream_open(model, &stream);
nemo_speech_diar_stream_push_f32(stream, samples, n, 16000);   // порциями — так получаем прогресс
nemo_speech_diar_stream_finish(stream);
nemo_speech_diar_segments(stream, &seg_cfg /* onset, offset, pad, min_gap, min_duration */, out, cap, &count);
```

Готовый GGUF `Nemotron-3-Diarization.q8_0.gguf` (107 МБ) лежит прямо в репозитории модели на HF.

**Сборка под Android** (официальных Android-пресетов нет, только `cpu-diar`, `vulkan-diar` и т. п.).
Как сделано в `core-diarization`:

1. Исходники подключены git-сабмодулями в `src/android/third_party`, коммиты зафиксированы:
   NeMo-Speech.cpp `536b17a` (0.3.0), llama.cpp `bd4f514` (тот же, что закреплён в NeMo-Speech.cpp),
   SentencePiece v0.2.2.
2. Их CMake опирается на `CMAKE_SOURCE_DIR` и не подключается через `add_subdirectory`. Поэтому в
   `src/main/cpp/CMakeLists.txt` цели `nemo_speech_common / runtime_ggml / asr + c_api` собраны заново
   и вместе с ggml и SentencePiece вшиты в одну `libsteno_diar.so`. Наружу видны только JNI-функции
   (`--exclude-libs,ALL`), неиспользуемый код выкидывается (`--gc-sections`).
3. ggml собирается только с CPU-бэкендом, `-march=armv8.2-a+dotprod+fp16`, без OpenMP, с
   llamafile-SGEMM. Патчи NVIDIA к ggml (в основном про CUDA) выключены: `GGML_PATCHED=OFF`, как в
   их пресете `vulkan-diar`. Нативный код оптимизируется (`-O2`) даже в debug-сборке приложения.
4. SentencePiece самой диаризации не нужен, но ASR-код NeMo в той же библиотеке на него ссылается
   при линковке.
5. JNI-мост `diar_jni.cpp` поверх `diar.h`: `create / stream_open / push / finish / segments / close / destroy`.
   Kotlin `NemotronDiarizer` подаёт звук порциями по 2 с (это шаг прогресса и отмены), пресет
   `v3-offline`, модель грузится на один вызов и сразу освобождается.
6. Параметры постобработки (`onset`, `offset`, `min_duration` и др.) вынесены в
   `NemotronDiarizer.Segmentation`. Пока стоят значения NVIDIA (CALLHOME), подбираем на своих данных
   под короткие реплики и перебивания. Среди них `pad_onset = 0.229` с: реплика начинается на ~230 мс
   раньше речи. Для нарезки под ASR это запас, чтобы не резать первое слово; для оценки границ —
   систематический сдвиг, который можно убрать уже после ASR по таймкодам слов.
7. Рецепту хватает CMake 3.22 — версии, которую AGP скачивает сам, поэтому сборка из исходников не
   требует ручной установки ничего, кроме `git submodule update`. NDK у всех модулей один
   (`ndkVersion` в convention-плагинах), им же AGP вырезает отладочные символы: в APK `.so` весит 1.9 МБ.

**Проверено** на эмуляторе Pixel 9a (arm64, 4 ядра, хост Apple M5): синтетический диалог 32 с, два
голоса, 7 реплик — 7 сегментов, спикеры не перепутаны, DER 0 % с collar 250 мс, RTF 0.046, пиковая
память процесса 256 МБ. Подробности и оговорки — в [TEST_RESULTS.md](TEST_RESULTS.md).

**Риск по языку.** В обучающих данных русского почти нет. Диаризация в основном акустическая и
должна переноситься, но это обязательно проверяем на своих русских диалогах.

**План Б**, если NDK-сборка не взлетит за день:

- (а) pyannote-segmentation-3.0 + speaker embedding + кластеризация из sherpa-onnx. Работает на
  Android из коробки, DER хуже, зато гарантированно;
- (б) ONNX-экспорт Sortformer из NeMo и свой AOSC на Kotlin. Дорого, крайний случай.

sherpa-onnx Sortformer **не поддерживает**: в репозитории есть только Nemotron ASR (проверено поиском
по коду).

### Локальная LLM — обязательна по ТЗ

> **Итог:** протокол встречи на LFM3-1.7B с нашей LoRA, подробно — [LLM_PROTOCOL.md](LLM_PROTOCOL.md).
> Ниже — исходный анализ.

**Чего LLM делать нельзя:** переписывать слова. WER даёт 40 баллов, а маленькая модель легко
«исправит» правильное слово. Поэтому контракт `TranscriptPostProcessor` в domain такой:

- менять можно только пунктуацию, регистр и метаданные;
- реализация сравнивает нормализованные последовательности слов до и после и откатывает реплику,
  если слова изменились;
- если LLM упала, конвейер всё равно отдаёт расшифровку с предупреждением (уже реализовано и
  покрыто тестом).

**Где LLM реально полезна:**

1. Пунктуация и регистр, если выберем ASR без e2e (`rnnt`).
2. «Протокол заседания»: краткое содержание, решения, задачи. Это прямо сюжет задачи («протоколов
   было так много, что котята трудились, не покладая лапок»), хороший UX и аргумент на защите.
   Отдельной кнопкой, вне основного замера времени.
3. Имена говорящих, если они представились («Я Барсик…»). Показываем в UI, в JSON остаются `speaker_N`.

**Рантайм: llama.cpp.** Он уже подключён сабмодулем в NeMo-Speech.cpp, значит ggml общий, и
диаризацию с LLM можно собрать в одну нативную библиотеку.

**Модель** — 1–2B instruct с хорошим русским, GGUF Q4_K_M (0.5–1.2 ГБ). Кандидатов (Qwen3-1.7B,
Gemma-3-1B-it и т. п.) сравниваем на своих данных по качеству пунктуации и скорости.

## Компоненты

Clean Architecture, многомодульность, раскладка `app` + `sources/{common, core, feature}`.
Слои разделены **модулями**, поэтому правила зависимостей проверяет компилятор, а не ревью.

```
src/android/
├── app/                         composition root: Application, граф Metro, MainActivity, навигация
├── build-logic/                 convention-плагины steno.android.* / steno.jvm.library
└── sources/
    ├── common/                  платформенная инфраструктура, не знает о предметной области
    │   ├── common-uikit         дизайн-система (токены, тема, компоненты), UdfViewModel
    │   ├── common-audio         декодирование (MediaCodec) и ресемплинг в моно 16 кГц
    │   └── common-models        доставка весов: assets → noBackupFilesDir, подкладывание через adb
    ├── core/
    │   ├── core-model           [JVM] сущности: Transcript, Utterance, SpeakerId, PcmAudio, AudioRef
    │   ├── core-domain          [JVM] порты движков и репозиториев, use case'ы, ChunkPlanner, TranscriptAssembler
    │   ├── core-data            реализации репозиториев: аудио, экспорт JSON/TXT/SRT
    │   ├── core-asr             GigaAM-v3 через sherpa-onnx            → SpeechRecognizer
    │   ├── core-diarization     Nemotron через NeMo-Speech.cpp + JNI   → Diarizer
    │   └── core-llm             llama.cpp + JNI                        → TranscriptPostProcessor
    └── feature/                 только presentation
        ├── feature-home         выбор файла / запись, статус моделей
        └── feature-transcript   прогресс, результат, экспорт
```

**Правила зависимостей:**

```
feature-*  ──►  core-domain ──► core-model          (+ common-uikit)
core-data, core-asr, core-diarization, core-llm  ──►  core-domain   (+ common-audio для core-data)
app  ──►  всё (только чтобы собрать граф)
```

- `core-model` и `core-domain` — чистые Kotlin/JVM-модули, Android туда не подключить.
- Фича получает use case'ы и не знает, чем они реализованы. `steno.android.feature` подключает
  только `core-domain` и `common-uikit`.
- Реализации регистрируются через Metro `@ContributesBinding(AppScope::class)`, граф собирается в
  `:app`. Чтобы заменить движок (например, на план Б для диаризации), достаточно поменять модуль в
  зависимостях `:app`, фичи и domain не трогаются.

## Основные технические решения

**Presentation: MVVM + однонаправленный поток данных.** Все экраны наследуют `UdfViewModel<State, Action, Effect>`:

- один `StateFlow<State>` — источник правды для UI;
- один вход `onAction(Action)`;
- одноразовые `Effect` (навигация, системные диалоги, снекбары) идут через `Channel`.

MVI-фреймворки (MVIKotlin, Orbit) не берём: основная сложность у нас в нативном конвейере, а не в
стейт-машине экрана. Тонкость Metro: наследник `UdfViewModel` регистрируется как
`@ContributesIntoMap(AppScope::class, binding<ViewModel>())`, иначе привяжется к промежуточному типу.

**DI: Metro 1.5.2.** Compile-time DI в виде плагина компилятора Kotlin, без kapt и KSP. Ошибка графа
ловится на компиляции. Агрегация `@Contributes*` по модулям в духе Anvil. Для Android используем
`metrox-android` (конструкторная инъекция в Activity через `AppComponentFactory`, отсюда minSdk 28)
и `metrox-viewmodel-compose` (`metroViewModel()`, `assistedMetroViewModel()`).

**Навигация: Navigation 3.** Back stack — обычный список `NavKey`. Декоратор
`rememberViewModelStoreNavEntryDecorator` даёт каждому экрану свои ViewModel. Фичи не зависят друг
от друга: экран отдаёт колбэки, переходы связывает `:app`.

**Стек и версии:** AGP 9.2.1 со встроенным Kotlin, Kotlin 2.4.20, Gradle 9.5.1, JDK 21, compileSdk 37,
minSdk 28, Compose BOM 2026.09.00. Версия Kotlin привязана к таблице совместимости Metro.

**Фоновая обработка.** Сейчас конвейер работает в `viewModelScope`. Для релиза его стоит перенести в
WorkManager с foreground service типа `mediaProcessing`, чтобы обработка не обрывалась при
сворачивании и чтобы показывать прогресс в уведомлении.

**Нативный слой.** `libsteno_diar.so` (NeMo-Speech.cpp + ggml), `libsteno_llm.so` (свежий llama.cpp с LFM3,
отдельный сабмодуль) и AAR sherpa-onnx со статически слинкованным ONNX Runtime. ABI: `arm64-v8a` (телефоны) и
`x86_64` (стандартный эмулятор; ggml без AVX2/FMA — эмулятор их не отдаёт гостю).

**Дизайн-система (`common-uikit`).** Собственная, не Material 3: экраны собираются только из её компонентов.
- `foundation/token` — отступы (сетка 4dp), размеры, радиусы, длительности анимаций;
  `foundation/theme` — цвета для светлой и тёмной тем (основной голубой, все текстовые пары проходят WCAG AA,
  8 цветов спикеров) и типографика на Golos Text с табличными цифрами для таймкодов; `StenoTheme`.
- `foundation/icon` — свой набор SVG-иконок (`res/drawable/ic_steno_*`), Material Icons не используем.
- `components` — `StenoScaffold` с тостами, `StenoTopBar`, `StenoButton`, `StenoIconButton`, `StenoCard`,
  `StenoProgressBar`, `StenoStatePanel`, `SpeakerBadge`, `StatusDot`, `StenoInfoRow`, `StenoText`.
- Из Material 3 остался только ripple внутри темы. Значения токенов предварительные: их заменит макет
  из Claude Design.

**Статический анализ — detekt 1.23.8**, перенесён из CuApp: конфиг `src/android/config/detekt/detekt.yml`,
конвенция `steno.detekt` (без `DetektPlugin.apply()`, совместима с Gradle 10), detekt-formatting и свои
правила в модуле `:detekt-rules`:
- `NoLocalDesignValue` — «сырые» dp, sp, цвета и доли разрешены только в `foundation/token` и `foundation/theme`;
- `NoInlineFqnReference` — полные имена классов только в импортах;
- `NoEmptyInteractiveAction` — в дизайн-системе нет пустых `onClick`;
- `DetektRuleIssueAsProperty` — защита самих правил от NPE при загрузке.

Плюс `ForbiddenImport`: `androidx.compose.material3.*` разрешён только в `common-uikit`. Архитектурные правила
CuApp не переносили: они завязаны на его граф модулей, а слои у нас и так разведены модулями Gradle.

### Поставка моделей

Эксперты ставят APK и сразу работают офлайн, поэтому **модели лежат внутри APK**:

- в `assets` без сжатия (`androidResources.noCompress += listOf("onnx", "gguf")`);
- при первом запуске копируются в `noBackupFilesDir`, потому что ggml и llama.cpp мапят файл по пути
  (экран прогресса для этого шага — в онбординге).

Бюджет: GigaAM-v3 int8 232 МБ + Nemotron 107 МБ + LLM 0.5–1.2 ГБ (оценка) + нативные библиотеки 26 МБ,
то есть APK ≈ 0.9–1.6 ГБ. Без LLM debug-APK сейчас весит ~400 МБ. Держим меньше 2 ГБ. Веса в git не коммитим:
[`tools/fetch_models.sh`](../tools/fetch_models.sh) качает их по зафиксированной ревизии Hugging Face
и сверяет SHA-256. Распаковкой и поиском файлов занимается `ModelInstaller` из `common-models`. Для
разработки модель можно подложить через adb (`fetch_models.sh --adb`), чтобы не пересобирать APK со 100+ МБ весов.

## Производительность (RTF)

- Модели загружаем и выгружаем последовательно: диаризация, потом ASR, потом LLM. Пик памяти —
  одна модель, а не три сразу.
- Тишину не распознаём: `ChunkPlanner` пропускает паузы длиннее 1 с.
- Потоки: ONNX Runtime intra-op = 4, ggml threads = 4, только большие ядра.
- Дальше, если будет время: ASR на готовых фрагментах параллельно с диаризацией (потоковый пресет
  Nemotron), XNNPACK или QNN для ONNX Runtime, OpenCL (Adreno) или Vulkan для ggml. Это пункты
  «Ultra Pro Max» про аппаратное ускорение.

## Оценка качества (наш стенд)

Эталоны организаторов увидим только на проверке, поэтому нужен свой стенд, иначе выбор модели и
параметров идёт вслепую:

1. Набор: русские диалоги на 2–4 человека (записать самим + открытые корпуса), разметка в формате ТЗ.
2. Пакетный режим приложения: debug-интент прогоняет папку и пишет JSON и тайминги каждого этапа.
3. Скрипт метрик: WER (jiwer, с той же нормализацией, что у организаторов), DER (pyannote.metrics),
   ошибка границ реплик, RTF. Результаты пишутся в `artifacts/test-results/results.csv`.

## Безопасность и приватность

- В манифесте **нет разрешения INTERNET** (`tools:node="remove"` на случай, если его принесёт
  библиотека). Офлайн проверяется по манифесту, а не на честном слове. Хороший аргумент на защите.
- Записи и расшифровки остаются в песочнице приложения. Наружу файл уходит только через системный
  диалог «Сохранить как» (SAF) по действию пользователя.
- `allowBackup=false`: расшифровки разговоров не уходят в облачный бэкап.

## Идеи для UX (пункты «средний уровень» и «Ultra Pro Max» из ТЗ)

- Плеер (Media3) с подсветкой текущей реплики и переходом к реплике по тапу.
- Переименование и цвета говорящих.
- Редактирование реплики и повторное распознавание отдельного фрагмента.
- Экран «Протокол заседания» от LLM.
- История расшифровок (Room) и запись с микрофона прямо в приложении.
- Экран «О моделях»: версии, хэши, наши метрики. Помогает на защите.
